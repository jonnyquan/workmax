# Releasing WorkMax

WorkMax is pre-1.0. Only a maintainer may publish an official release. A release
must be reproducible from a clean checkout and must include the corresponding
source and license materials for every distributed artifact.

## 1. Prepare the release

1. Start from a clean checkout of the intended commit.
2. Confirm CI and the full-history secret scan pass.
3. Review `CHANGELOG.md`, move relevant entries from `Unreleased` into a dated
   version section, and update comparison links.
4. Update the Desktop version and any Server/Desktop protocol versions together.
5. Confirm `support@workmax.app` and private vulnerability reporting are
   monitored.

Run:

```bash
make doctor
make bootstrap
make verify-core
make license-audit
make package-preflight
```

Do not release when a dependency is available only through a local `replace`,
when a third-party asset has unknown provenance, or when any required check is
skipped without a documented maintainer decision.

## 2. Build distributable artifacts

Build from the tagged commit, not from an uncommitted workspace. For macOS:

```bash
npm --prefix desktop/electron run dist:mac:public:arm64
npm --prefix desktop/electron run dist:mac:public:x64
```

The build generates and packages:

- the complete WorkMax `LICENSE`;
- `THIRD_PARTY_NOTICES.md`;
- the Go dependency license bundle generated by `go-licenses`; and
- Electron's license and Chromium third-party notices.

Run notarization only through the repository's notarization script. Never put
signing or notarization credentials in the repository, workflow logs, release
archives, or support bundles.

Server binaries must be accompanied by the same `LICENSE`,
`THIRD_PARTY_NOTICES.md`, generated Go dependency bundle, configuration schema,
and exact source revision used to build them.

## 3. Verify AGPL source availability

- The public source archive must contain everything needed to build the exact
  released Server and Desktop binaries, excluding ordinary system libraries and
  secrets.
- The Desktop source-code link must point to the public repository containing
  the released revision.
- Operators distributing or running modified network-accessible versions are
  responsible for prominently offering their corresponding modified source to
  remote users as required by AGPL section 13.
- Preserve all third-party notices and generated license material.

## 4. Sign and publish

1. Create SHA-256 checksums for every binary archive and installer.
2. Verify macOS Developer ID signatures, notarization tickets, and stapling.
3. Create an annotated `vMAJOR.MINOR.PATCH` tag from the reviewed commit.
4. Publish release notes from the matching changelog section.
5. Attach binaries, checksums, and any detached signatures to the release.
6. Download the published artifacts on a clean machine and repeat package and
   smoke verification before announcing the release.

Releases are immutable. Correct a faulty release with a new version; do not
silently replace published binaries under an existing tag.
